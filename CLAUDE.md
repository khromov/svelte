# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Also read [`AGENTS.md`](./AGENTS.md) and [`CONTRIBUTING.md`](./CONTRIBUTING.md) — this file covers what they don't.

## Repository layout

pnpm workspace monorepo. `packages/svelte` is the only published package and contains essentially all the code; `playgrounds/sandbox` is a scratch app for manual testing, `benchmarking/` holds perf benchmarks, `documentation/` holds the docs that get published to svelte.dev.

## Commands

Run from the repo root unless noted.

```sh
pnpm test                          # full vitest run
pnpm test runtime-runes            # one suite (positional arg is a path filter)
pnpm test validator -t a11y-alt-text
FILTER=my-sample pnpm test validator   # filter by sample dir name; faster/more compact than -t
UPDATE_SNAPSHOTS=true pnpm test snapshot   # regenerate .expected/_expected fixtures
SVELTE_NO_ASYNC=true pnpm test runtime-runes  # what CI's TestNoAsync job runs

pnpm lint      # eslint + prettier --check
pnpm format    # prettier --write
pnpm check     # builds packages/svelte, then typechecks everything

pnpm bench                    # run benchmarks
pnpm bench:compare main foo   # compare two branches (see the performance-investigation skill)
```

Inside `packages/svelte`:

```sh
pnpm build            # rollup UMD compiler bundle + generate + treeshakeability check
pnpm dev              # watch mode
pnpm check            # tsc over runtime, compiler, and tests/types
pnpm generate:types   # regenerate types/ (checked in — CI fails if stale)
```

Prerequisite for the browser suites: `pnpm playwright install chromium`.

Run `npx changeset` at the root for any change that should trigger a version bump.

## Generated files — do not edit by hand

- `src/compiler/errors.js`, `src/compiler/warnings.js`, `src/internal/{client,server,shared}/{errors,warnings}.js` are generated by `scripts/process-messages` from the markdown in `packages/svelte/messages/**`. Edit the markdown; the same script also writes `documentation/docs/98-reference/.generated`.
- `packages/svelte/types/` is generated by `pnpm generate:types` (dts-buddy) but checked in, so CI diffs it.
- `src/version.js` is written at release time.
- `documentation/docs/07-misc/.generated/` comes from `pnpm generate:browser-support`.
- Top-level `*.d.ts` shims and `compiler/index.js` are build artifacts (gitignored).

## Compiler architecture

`src/compiler/index.js` exposes `compile`, `compileModule`, `parse`, `parseCss`, `preprocess`, `migrate`, `print`. `compile` runs three phases in `src/compiler/phases/`:

1. **`1-parse/`** — hand-written template parser (`state/` for fragment/element/tag/text, `read/` for script/style/expression/options) using acorn (+ `@sveltejs/acorn-typescript`) for embedded JS. TypeScript is stripped after parse via `remove_typescript_nodes.js`. Produces the modern AST; `legacy.js` converts it to the Svelte 4 AST when `modern: false`.
2. **`2-analyze/`** — builds scopes (`scope.js`), binds references, validates, emits warnings, and analyzes CSS for scoping/pruning. One visitor file per node type in `2-analyze/visitors/`. Attaches a `metadata` object to nodes that phase 3 reads.
3. **`3-transform/`** — two independent backends, `client/` and `server/`, each a zimmerframe visitor set over the AST emitting an ESTree program (printed with esrap). The client backend also builds cloneable DOM templates in `transform-template/`. `shared/` holds logic both backends need (assignments, async transform).

Adding template syntax generally means touching all three phases plus both transform backends, plus a message in `messages/compile-errors|compile-warnings`.

## Runtime architecture

Three runtime trees under `src/internal/`, kept strictly separate:

- **`client/`** — the signals runtime. `reactivity/` holds the core: `sources.js` (writable state), `deriveds.js`, `effects.js`, `batch.js` (scheduling/flushing, async batches), `status.js`, `props.js`. `runtime.js` drives dependency tracking and effect execution; `proxy.js` implements deep `$state` reactivity. `dom/` renders: `blocks/` for each control-flow construct (`if`, `each`, `await`, `key`, `snippet`, `boundary`, …), `elements/` for attributes/bindings/events/transitions, plus `hydration.js` and `template.js`. Compiled client output imports from here.
- **`server/`** — SSR. `renderer.js` builds a tree of `string | Renderer` nodes so async work can be awaited and collected in order; `hydration.js` emits the hydration markers the client reads back.
- **`shared/`** — the small set of helpers both use.

Public entry points (`svelte`, `svelte/store`, `svelte/reactivity`, `svelte/legacy`) have separate `index-client.js` / `index-server.js` files wired up through the `exports` map in `packages/svelte/package.json`. Adding a new subpath export means updating that map — the root `vitest.config.js` resolves `svelte/*` imports in tests through it.

Internal cross-package imports use the `#client`, `#server`, `#shared`, `#compiler` subpath imports declared in `package.json`.

## Tests

Everything lives in `packages/svelte/tests/`. Most suites are directory-driven: a `test.ts` calls `suite()`/`suite_with_variants()` from `tests/suite.ts`, which iterates `samples/*/` and reads an optional `_config.js` per sample. To add a test, add a sample directory — no registration needed.

- **`runtime-runes/`, `runtime-legacy/`** (the two big ones) share `runtime-legacy/shared.ts` and run every sample in four variants: `dom`, `hydrate`, `ssr`, `async-ssr`. A `_config.js` can narrow this with `mode` / `skip_mode`, and `skip_async` / `skip_no_async` for the `SVELTE_NO_ASYNC` split.
- **`snapshot/`, `parser-modern/`, `parser-legacy/`, `print/`, `css/`** assert generated output against checked-in `_expected/` fixtures — update with `UPDATE_SNAPSHOTS=true`.
- **`validator/`, `compiler-errors/`** assert warnings/errors against `warnings.json` / `errors.json` next to the sample.
- **`runtime-browser/`** drives real Chromium via Playwright (bundled with esbuild); everything else runs in jsdom.
- **`signals/`, `store/`, `motion/`, `types/`** and `*.test.ts` files colocated in `src/` are ordinary unit tests.

Compilation for sample-based suites goes through `tests/helpers.js#compile_directory`, which writes to `<sample>/_output/{client,server}/` — useful for eyeballing what the compiler produced for a failing test. `_output` is scratch; `_expected` is the assertion.

## Conventions

- `snake_case` for internal names, `camelCase` for public API — enforced by `eslint-plugin-lube`.
- A custom eslint rule forbids importing compiler code (`../compiler/`, `#compiler`) from runtime code, including type-only imports.
- Source is JavaScript with JSDoc types, not TypeScript. Use `/** @import { Foo } from '...' */` for type imports.
- Prettier: tabs, single quotes, no trailing commas, 100 columns.
- `no-console` is an error.
